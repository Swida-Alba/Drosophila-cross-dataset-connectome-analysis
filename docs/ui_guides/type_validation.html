Type Validation (TM VEV)

BodyId-level validation of a source → target type mapping between two connectomes (e.g. flywire_FAFB_v783 vs male-cns:v1.0). It verifies the mapper’s claimed branches against real connectivity, expands candidate neurons, and renders 3D review scenes. Everything it produces is a proposal - the mapping itself is never rewritten.

Where it fits

This is the validation counterpart to the Cross-Dataset Comparison (Paths) tab. Paths compares connectivity across datasets; Type Validation checks whether a proposed type mapping between a source and a target dataset actually holds at the neuron level. Read the type-level preview, then validate at bodyId resolution.

Quick start

  1. Pick a Source Dataset and a Target Dataset. They must differ — the run refuses same-dataset pairs at the door.
  2. Add one or more Source Types / Categories as chips: a neuron type (APDN3, s-CPDN3A) or a coarse cell_type category (circadian_clock). A query is required — an empty query is rejected before the run starts.
  3. Choose a Validation Mode: restrictive ⊆ family ⊆ aggressive. The three nested modes are the buttons in the Validation Mode card; the Parallel mode card beside them holds the fourth. All four sit on one row, and the card seam between them is deliberate — it is the UI saying the fourth is not one more rung. Wider modes admit more candidate bins (aggressive adds the deep-window examinees bin — whose rows live in deep_candidates.csv; examinees.csv itself is the mode-invariant per-pair pool-edge table) and run slower. That fourth button, pooling, is not a wider rung: it is a parallel unsupervised search that scans the queried population against the whole target universe, keeps each source’s top-N rows under its own admission bar, writes its result into pooling/ beside the nested bins, and changes none of them. Selecting it reveals its own card (the bar metric and depth, the two floors and the rank window, the morph budget); the other modes never read those knobs. The bar admits; the floors only flag. Each source keeps the top-N rows of the metric it chose (either is the union of both metrics’ own top-N), and the Jaccard / rank_union floors and the window are then measured against every admitted row and exported as flags that remove nothing — they were filters until one of them, at its own default, was measured starving 119 of 242 queried sources. Every pooling export prints a per-row tier on the ladder matched / verified / nominated. Morphology is the last gate and a mandatory one — a pooling run with Morphology off is refused at the door: a candidate scored below its bar leaves the exported pool and the scene root, while a row whose target morphology produced no verdict (no measurement, e.g. past the budget’s not-attempted cap) never leaves — a missing measurement is not a rejection. A pass that raised or graded nothing did not gate the pool (gate_applied false: its tiers are unrefused, not passed). The budget that priced the pass is published with its rule (0 = auto, three scoring units per queried source).
  4. Toggle Stages as needed (morphology, 3D scenes, backward reciprocal evidence, out-map expansion, verify suspects — an advisory re-check written to mapping/suspects_verification.csv) and set the offline behaviour in Data & Offline. The collapsed Advanced Settings card holds the deeper knobs (morph AUC floor, neuron alpha, per-stage numerics); the defaults are fine for a first pass.
  5. Click Run Validation. When it completes, open report.html, the run folder, or the latest 3D scene from the action row.

Cost & scope

Validation scans each source neuron against the full target universe (140–180k neurons). A coarse category, aggressive mode, or backward reciprocal evidence each multiply runtime - a single backward reverse scan is roughly 4–7 s with a budget in the hundreds of neurons. Start with a type-level restrictive pass. 3D scenes default to Max scenes = 0, which renders one page per parent type - a coarse category therefore pays for every scene it resolves. Set a positive cap (the run names the parents it drops) or split a broad query into separate runs.

Advanced Visualization (the review scenes)

A collapsed card between Stages and Data & Offline, shown only while Render 3D review scenes is on — the same panel the analysis tabs use, scoped to what a branch scene can honor. The look the pipeline fixes is fixed here too — line mode, the opacity default, show-figure off and export-views on — so with a default Settings profile a run renders what it did before this card existed. Background and Simplification Method follow your saved global preference as they do in the other analysis tabs; the shipped defaults for both match the renderer’s, so only a preference you changed yourself will look different.

  • Skeleton Mode starts at line for speed; tube is the detailed mesh, and it then exposes Simplification Method / Mesh Simplification — these scenes inject skeletons the pipeline already loaded, so simplification is what keeps a tube render of a hundred neurons from stalling the browser. In line mode the served geometry is guaranteed to match the label: every scene neuron loads as a centerline skeleton (FAFB targets via the CAVE-skeleton path with the extrusion check on, never the prepared mesh), and the run's scene self-check flags any leaf that would render mesh-only. A parent whose queried sources all fail to load skeletons writes SCENE_FAILED.txt instead of rendering a target-only picture.
  • Category Colors paint the legend by category, not by layer: one row per bin (query, matched, verified, borderline, unmatched, sibling, candidates, family, relative, examinees, source-candidates, out-map candidates, unassigned, pooling), each seeded from the pipeline’s own palette so the UI never owns a second copy of it. A category keeps its color across every branch and parent in the run — that is what makes two scenes comparable — so recoloring moves the whole bin, and query also drives the out-map query root. Colors carry no alpha unless you opt into it: each row is the same color cell the Visualization › Skeleton layer editor uses — a swatch that previews the current color and opens the shared picker (Bokeh palettes with strip previews, a color grid, and an Override alpha control), beside an editable value that commits on Enter or blur. One picker serves every row. Without an explicit alpha, Neuron Opacity is the only opacity control; with one, that category alone overrides it.
  • Background, Export Method, Export Scale, Export Views (on, so each page still gets its PNG preview beside it) and Show Figure (off, because a batch run would open every scene).
  • Not offered, because the scene’s correctness depends on them: the tree legend (it carries branch → category → bodyId), the native template (it is the coordinate frame the bridged targets were delivered in), the synapse skip, and the scene count — which stays Max scenes on the Stages card. Neuron alpha moved into this card, so it has exactly one owner.

What a run actually wore is recorded in parameters.json as neuron_alpha, scene_viz and scene_category_colors — and with scenes on those are the effective values, not an echo of what was sent: the resolved styling the renderer received ({} when nothing was moved) and the full legend palette, defaults and alias propagation included. The command line reaches the same record through --scene-viz-json / --scene-colors-json, so a run is reproducible from its own provenance file.

Offline runs

Use connection cache is not an offline switch - turning it off only forces a refetch. To stay offline, check Cache-only profiles (skip online profile build), and also turn Morphology verification and Render 3D review scenes off (stage-2 profiles, morph vectors and skeleton loads are what reach the network). An unsupported dataset pair is not an error - it resolves to zero branches and an empty run, so check the log for “no valid type pairs resolved; nothing to validate” — the UI also raises a persistent Completed, but nothing resolved notice and a Set coverage banner driven by set_coverage.json.

The report

report.html carries fourteen tabs, including Coverage (the three-level L1 claim / L2 provenance / L3 validation counts), the per-bin results, Out-map (fill proposals for unclaimed sources), Backward (reciprocal grades) with a separate Backward source status view (per-source statuses over the target pool), the Homolog · forward / Homolog · backward per-bodyId match sheets (below), Morph and Scenes. The Scenes tab also prints the palette this run actually wore — one chip per category, and any bin you recolored names the default it replaced — so a recolor is readable from the report, not only from each scene’s own tree legend. Terms carry hover glossary entries; warnings are also collected in user_warning_notes.txt. Every table renders all of its rows in one scrollable table — there is no hidden “Show all” second table anywhere.

Homolog · forward / backward (per-bodyId match sheets)

Where the Reciprocal tab grades the neurons the mapping did not assert, the two Homolog tabs answer the matching question for every bodyId the run touched, both directions — the worksheet for manually allocating candidates / family / relative / examinees and every other appeared bodyId. Homolog · forward (validation/forward_matches.csv) is one row per appeared source bodyId with its chain-best target and its allocation group; Homolog · backward (expansion/target_matches.csv) is the exact mirror: every appeared target bodyId — pool members included, which the reciprocal pass deliberately leaves unscanned — scanned back against the whole source dataset (stage 5e). Hover a primary match for the union of the top-3 rank_union and top-3 jaccard hits, and read the pair’s morph qualification from the run’s own exports (display only — nothing is re-scored; not scored when absent). Type columns read untyped for unannotated neurons, never the raw profiler “nan”. Advisory display data: nothing downstream gates on it.

Backward (reciprocal) evidence

Backward (reciprocal) homolog evidence is ON by default (user 2026-09-26; uncheck to skip). With it on, stage 5d asks the same homolog question from the other side: each candidates / family / relative member - and, by default, each unmatched pool member - is reverse-scanned against the whole source universe. Already-mapped members (matched / verified / borderline) are skipped, because their forward pair already is the symmetric evidence; that is why the only pool-side toggle is Backward scans unmatched pool members. Each scanned neuron gets an advisory high / medium / low grade for how prominently its own branch’s source type ranks in that reverse scan — in either ranking, so the grade is pure rank evidence with no score threshold. It never moves a neuron between bins and never counts toward a fill. Read it in the report’s Reciprocal tab (one row per neuron, ordered by the Jaccard of the branch-type hit the grade rests on, so a neuron with no such hit sinks below the ones that have one; it is shown beside the global top-1) or in expansion/backward_matches.csv.

Output

The run lands in <output>/type-map-validation_{SRC}_to_{TGT}_{timestamp}/ with validation/, expansion/, gap_fill/, mapping/ CSV/JSON deliverables, a report.html, and visualization/plot-3d_*/ scene folders. The pair_summary.csv and gap_fill_dedup.csv are previewable in the Output Files panel.
