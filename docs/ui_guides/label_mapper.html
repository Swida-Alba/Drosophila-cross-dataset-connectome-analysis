Custom Type Mappings

Group neuron types across datasets into custom groups for cross-dataset comparison and pathfinding (LabelMapper format).

UI workflow

Mappings are built inline on each tab — no scripting needed:

  1. Open the tab's mapping panel. The Cross-Dataset Comparison tab mounts it as Custom Mapping; Complete Paths, Network and Shortest Paths mount it as Custom Grouping, and Connectivity's Comparison sub-tab as Custom Grouping Preset (the Settings tab's Custom Type Mappings card offers the same editor). Choose the Target datasets where offered, then edit the board — one row per custom group, one aligned member input per selected dataset, outlined chip fields, dataset-aware type-ahead with a Recent list in each member input (a pick keeps that query's rows on screen and ticks the names already added — in either list, and a ticked row takes its chip back out on the next click — and a Recent row hints at the column's own dataset when that name actually exists there), and a See available neurons lookup.
  2. Define your groups and run. At run time the board is exported to cache/user_mappings/_inline/<tab>_<timestamp>.json and passed to the run — as overall_mapping_json on the Cross-Dataset tab, where it acts as a mapping overlay (your explicit source/target neuron queries stay, and only neurons matching the mapping are renamed to their custom groups; unmapped neurons keep their identifiers), or as custom_mapping_file on the path/network tabs, where mapped neurons are grouped at type level via EnrichConnectionTable (custom_group columns). Residuals of collided native types (2026-10-08; the producer set was fixed 2026-10-13): when a native type's population is only partially governed — some of its neurons are mapper members, others are not — or the type name is itself one of the mapper's labels, the type resolver star-tags the unenrolled neurons as T* (native type + *), so they never silently merge into the governed population or into a same-spelling label. The key is terminal (never re-resolved, hemisphere suffix included) and deliberately undecorated, so what it stands for is published instead: the [label mapper residuals] line in user_warning_notes.txt, label_mapper_residuals.csv in the run folder and under comparison_report_used_data/, and the label_mapper_residuals record in all_attributes.json. Only lanes that can see the dataset's neuron table assign the key; readers consume it as exported, and every export keeps the raw native type beside it (native_type_pre/native_type_post). Without a local neuron table membership still applies and residuals are reported as NOT EVALUATED.
  3. Reuse a mapping later via Load… (parses any mapping JSON back onto the board, so a run is exactly reproducible from its exported file) or the history pulldown (below).
  4. Optional — save a named copy in Settings. The Settings tab's Custom Type Mappings card adds a Save Mapping action that writes the stable Custom Mapping preset to cache/user_mappings.json (gitignored) and exports it to cache/user_mappings/. Saving does not attach the preset to future runs — no tab auto-loads saved presets; bring the JSON back onto a board with Load… when you want it.

Runs always consume the exported file, so results stay reproducible (label_map.json / parameters.json record the mapping used).

Inline groups & history (query-local grouper)

Every tab with a Custom Grouping button opens a popup panel (same design as the neuron-index viewer). The panel pairs a lightweight group editor — one row per label: a group name plus one neuron box per dataset — with a history pulldown of previously-used groups. Opening the panel seeds one empty row for first editing. Groups are recorded into history automatically (when pushed to a query or run); nothing is named or saved by hand.

  • Same label, all datasets: one label governs every dataset column on the board. On the Cross-Dataset tab the columns follow the selected datasets, and label names are compulsory (the shared label is what aligns datasets). On single-dataset tabs names are optional — blank rows auto-name to Group_N.
  • Uniform format: at run time the board is exported to the same LabelMapper JSON schema as presets, at cache/user_mappings/_inline/<tab>_<timestamp>.json. Scripts load that file directly: LabelMapper(overall_mapping_json="…") — no conversion.
  • Reload: Load… parses any mapping JSON (inline export, preset export, or hand-written) back onto the board, so a run is exactly reproducible from its exported file.
  • History pulldown: the former "preset" control is now a history list. Groups are recorded automatically — when a group is pushed to a query or exported at run time — into cache/user_mappings/group_history.json. Selecting an entry loads that group's members onto the board for reuse or editing; no name is asked and nothing is saved manually. Each entry also has an “x” that removes it from the history after a confirmation popup. A label maps to every dataset it was ever defined for; defining it again with different members covers (replaces) the previous value for the datasets on the board. Auto-named Group_N rows are never recorded.
  • Use groups in the query: each group row carries Add to Source / Add to Target (or Add to Query) buttons that append the group's label as a single chip to the tab's neuron inputs. The board's toolbar has a matching Add all button (the check-list icon beside Load…) that pushes every populated group at once, in board order, naming blank rows as Group_N the same way a single push does; a group with no members anywhere is skipped, and a board with nothing to add says so instead of touching the input. The backend expands that label into its member neurons, so a freshly defined group drives the run directly and the exported tables/visualizations aggregate under the group label. The buttons are not offered for an input the tab has disabled — in the Connectivity and Morphology Comparison sub-tabs, choosing Aggregation Level = custom group disables that query box because the rows come from the board itself, so pushing labels into it would change nothing. Rows re-render on every panel open, so the buttons follow the current level.
  • Which chips are groups: a chip that names a group is ambiguous on its face — DN1a reads identically whether it means the native type or the group you just defined — so the query input marks the chips that currently resolve as groups: the group glyph, a cobalt left rule and a deeper fill, with a tooltip giving the member counts in the board's own column order (Custom group DN1a — 4 in male-cns:v1.0, …) including datasets the tab is not showing as columns. The mark tracks the board — rename a group or delete its row and the chip in the query box goes back to looking like a literal query, which is exactly what it then is. It also tracks Match by: at any mode other than exact the chip is rewritten into a regex before the backend sees it, so the label stops expanding and the mark is withheld rather than promising a resolution that will not happen. The count badge follows the same rule and is the one surface that also covers an uploaded list — a file of group labels never becomes chips, so it reads 21 groups (or 26 neurons · 21 groups when literal queries are mixed in) instead of calling them neurons.
  • Apply Groups to Partner Keys (Connectivity ▸ Comparison only): the profiling comparer is the one grouping surface with a partner side — each neuron's profile is a map of partner keys to weights — so this control folds those keys through the groups (weights summed per label) and computes similarity over the group feature space instead of raw type names. It folds the type-level partner keys at whatever aggregation level the run ends up on (attaching a preset forces custom group), while bodyId-level matrices keep raw keys. The other grouping tabs have no partner side to collapse, which is why they offer no such control. It needs a mapper: with no preset attached the toggle is dropped and the run log says so.
Division of labor: the shared Custom Mapping panel writes aligned groups to the source and target roles. Empty boxes export as empty groups, which keeps cross-dataset validation happy when a label has members in only some datasets.

Mapping file format (JSON)

The exported mapping uses LabelMapper's native JSON schema — a top-level format tag naming the grammar, one mapping per role, a custom_label list of group names, and one list of group lists per dataset:

{
"format": "drocat_custom_groups/v1",
"source_mapping": {
  "custom_label": ["aMe12"],
  "hemibrain:v1.2.1": [["aMe12"]],
  "male-cns:v0.9": [["aMe12"]],
  "flywire_FAFB_v783": [["720575940610453042"]]
},
"target_mapping": {
  "custom_label": ["KCg-s1"],
  "hemibrain:v1.2.1": [["KCg-s1"]],
  "male-cns:v0.9": [["KCg-s1"]],
  "flywire_FAFB_v783": [["KCg-s1"]]
}
}
Only JSON is supported for overall_mapping_json. A role may be omitted (e.g. source-only mappings); at least one mapping key must be present. The format key is required for a preset a run reads: it names the grammar the grouping board writes, and a preset that omits it — or declares a grammar this build does not read — is refused with a clear error rather than parsed on shape alone (CSV role files and in-memory dictionaries make no such claim and stay accepted). Exports from this board, and LabelMapper.to_dict(), always write the tag.

CSV format (script use)

The CSV format is the most straightforward way to define mappings manually: a custom_label column plus one column per dataset. Cell values are specific neuron IDs or regex patterns (e.g. MBON14.*_R matches multiple neurons).

Why use custom groupings?

  • Consistency: compare "apples to apples" across datasets whose naming conventions differ (e.g. aMe12 in hemibrain vs aMe12-like in male-cns).
  • Simplicity: analysis code deals only with standard labels, not dataset-specific IDs (e.g. 720575940610453042).
  • Scalability: add new datasets by extending the mapping, without changing analysis code.

Display role: matrix axes and label views

Beyond defining comparison rows, a loaded preset acts as the tier-0 identity overlay on every comparison surface — a label IS the identity and is never re-resolved through the auto type mapper:

  • BodyId axes (Connectivity Comparison, Morphology Comparison, Cross-Dataset Morphology): a preset-resolved bodyId reads {bodyId}_{label}({native}) — e.g. 13531_5th-LNv(5thsLNv_LNd6_L) — with the legacy suffix, side marker included, inside the parentheses. When the label already IS the native name the parenthetical is dropped ({bodyId}_{label}, or {bodyId}_{label}_{L|R} when only the side differs). The bodyId stays the token before the first _ (axis parsers key on the head); unmapped members keep the legacy form byte-identically.
  • Cross-dataset morphology writes morph_labeltype_matrix.csv beside the native morph_type_matrix.csv (which stays native-keyed): one row per standard label, multi-label native types expanded, unmapped members keeping their native name. overview.csv gains a label column ('/'-joined for double-claim types).
  • Morphology Comparison members.csv gains a label column beside the native type — per-bodyId resolution, because a native type can settle to two labels while a bodyId resolves to exactly one.
Reproducibility: each run records the mapping file it consumed (label_map.json / parameters.json), so a mapping can be edited later without invalidating past results.
