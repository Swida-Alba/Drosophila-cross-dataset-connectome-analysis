Find Similar Neurons Morphology tab

Search for neurons similar to a query by morphology (skeleton shape) within one dataset. This is the Find Similar sub-tab of the Morphology tab; it is intra-dataset only. For connectivity-based similar search (including cross-dataset homolog search), use the Connectivity tab's Find Homolog sub-tab.

Morphological similarity

Two methods are available. Find Similar uses raw skeletons only. Raw skeletons are shared at cache/{dataset}/skeletons/raw_skeletons/; Find Similar's vector parquet remains under cache/{dataset}/find_similar/. The visualization simp90 cache is never used for comparison.

MethodCostNotes
Vector (spatial) (recommended)<10 ms per query Each neuron is reduced to a 256-dim shape + spatial feature vector. Scores are per-block cosine (0.30/0.70) on standardized + ZCA-whitened vectors, cached at find_similar/morphology/skeleton__vectors_v2.parquet (the vector_v2 scoring cache; its standardization stats and ZCA whitening live in meta_v2.json / whiten_v2.npz beside it); if a row is missing it is fetched online and vectorized.
NBLAST~5–15 s for 100 prefiltered candidates Canonical Costa et al. 2016 pairwise score via navis on raw skeletons only. Dotprops are rebuilt per query and never cached — no dotprops file is ever written to disk.

Dotprops were benchmarked on the 8,839-node raw aMe12 skeleton: building them with k=20 took about 28 ms, while a compressed serialized dotprops object was about 144 KB. A compressed raw skeleton was about 48 KB in the same benchmark, so dotprops caching would use more space while saving only tens of milliseconds per neuron. It is not enabled by default. NBLAST score caching was evaluated separately. A final pair-score cache would need a dataset revision, ordered bodyId pair, navis/NBLAST version, dotprop parameters, scale and scoring options in its key. In practice the reusable cost is raw skeleton/vector preparation; the current design keeps those assets and recomputes dotprops/scores so stale scores cannot survive a dataset or parameter change.

Candidate source

Level controls the result granularity. auto (default) follows the query kind: a type query returns type-to-type rows (each row = one target type), a bodyId query returns bodyId-to-bodyId rows. bodyid/type force a level for multi-neuron or mixed queries.

Candidate Source selects how candidates are discovered before morphological scoring:

  • auto (default): NeuPrint datasets (hemibrain, male-cns, ...) use the ROI-distribution screen: every neuron of the dataset is ranked by cosine similarity of its input/output synapse distributions over the dataset's primary ROIs (from {dataset}_allneurons_roi_count_df.parquet, or the legacy CSV from older pulls), comparing both orientations across the midline (bilateral mirror) so contralateral homologs match. This reaches every neuron — the connectivity screen below can never find neurons without shared partners (~8% of same-type members on male-cns). A one-time per-dataset matrix is cached (cache/{dataset}/morphology/roi_profiles.npz); the top screen-ranked types (bounded by Candidate Cap) are kept and expanded to all their member neurons; raw skeletons are then fetched for the pool and shared for reuse. FAFB uses healed raw skeletons or the CAVE fallback. BANC is not selectable for morphological find-similar: the public L2/full skeletons still need vector-quality validation, so the feature is deferred (BANC 3D visualization and pathfinding work). Mesh and simp90 visualization files are never candidates for either method.
  • roi: the ROI-distribution screen only. Requires the dataset's ROI-count table and metadata sidecar (missing sidecars are fetched and saved once automatically).
  • combined: union of the ROI screen and the connectivity (shared-partner) screen — the widest candidate pool and the highest recall per fetched skeleton, at the cost of more transient skeleton fetches.
  • profile: the connectivity screen only — candidates found directly in the connection cache (cache/{dataset}/connections.parquet: neurons sharing upstream/downstream partners with the query, ranked by shared-partner count).
  • cache: full-morphology over the complete local raw skeleton population (download raw skeletons first — see below).

Candidate Cap (default 500) is the single knob bounding how many candidates are ever compared: the sorted candidate list of the selected screen is truncated to this many neurons, which become the scoring pool (it also serves as the NBLAST prefilter of cache-mode searches; pure cache vector searches compare the whole local population). Fetched raw skeletons are always persisted as compressed .swc.zst files in the shared dataset cache at skeletons/raw_skeletons/ for reuse by every workflow. The computed raw vectors are persisted into the vector cache — the lookup order is vector cache, shared raw skeleton file, then online fetch, and a fetched neuron is never vectorized twice. Already-cached raw skeletons are reused and the query neuron is fetched if missing. ROI Filter (shown when the dataset's connection cache carries synapse location data — male-cns has 114 ROIs like AL(L), hemibrain has none) restricts the candidate rows of the connectivity screen (roi/combined discovery is dataset-wide by design). results.csv and type_summary.csv contain ALL compared candidates (bounded by the cap), each row carrying the screen evidence — roi_similarity (primary-ROI distribution cosine) and/or profile_similarity (normalized shared-partner count) — alongside similarity (morphology); Top N applies to the optional 3D visualization only. If no candidates are found, the search falls back to the vector cache when available.

Full-morphology mode & skeleton download

Use Settings → Dataset Cache → Download All Skeletons to download a complete raw skeleton population. The button sits beside Pull Complete Connections, before Cancel. New bulk files use compressed {bodyId}.swc.zst; legacy .swc.gz and pickle files remain readable. Both the download and vector-cache update are resumable. After a raw download, build the vector cache and run with Candidate Source = cache to compare the query against the entire local skeleton population. The healed FAFB skeleton bundle remains a local raw source and is vectorized without copying its SWC entries.

Skeleton vector caches

Two parquet caches live under cache/{dataset}/find_similar/morphology/: skeleton__vectors_v2.parquet is the vector_v2 scoring cache the Vector method scores from (with meta_v2.json / whiten_v2.npz), and skeleton_vectors.parquet is the shared pool-vector cache (~1 KB/neuron, ~30–50x smaller than the raw skeletons) that feeds the connectivity-expanded candidate prefilter. Both build incrementally from already-cached skeletons (~15–85 ms/neuron) and are auto-triggered on the first query. Without a vector cache, the connectivity-expanded search z-scores the pool vectors with pool-computed statistics so cosine scores stay scale-fair.

Similarity score formulas (morphology)

The three evidence columns are computed independently and are never mixed across candidate sources; the primary similarity column is the morphology score only.

ScoreFormulaRange
similarityvector_v2: per-block cosine (shape/spatial, 0.30/0.70) on standardized + ZCA-whitened vectors (a whitened cosine — it can be negative, though real pairs are typically positive); NBLAST: normalized pair score−1–1 for both (a whitened cosine and normalized NBLAST can both score below zero — less similar than chance)
roi_similarityROI-distribution screen score (candidate selection only, never in the morphology score): cosine of input/output synapse-distribution vectors over the primary ROIs, mirrored across the midline0–1
profile_similarityshared-count / max-shared-count (normalized shared-partner count)0–1
intra_type_similaritymean pairwise similarity of the type's members (the intra-type reference)0–1

For the vector method, each neuron is reduced to ~24 morphometrics plus a 100-dim persistence block; the pool is z-scored with pool-computed statistics so cosine scores stay scale-fair.

Contralateral (mirror) handling

NBLAST matches arbors in absolute coordinates, so a neuron and its mirror twin sit far apart: contralateral same-type pairs score at chance (benchmark median −0.03 vs 0.89 ipsilateral; partner reciprocal rank 0.13 vs 0.84). NBLAST type means therefore use ipsilateral pairs only: rows pairing opposite known sides (somaSide, or hemisphere on FlyWire) are excluded from type_summary.csv, while results.csv keeps every pair row for inspection. Types whose only NBLAST evidence is contralateral are omitted from the type ranking, and n_bodyids counts ipsilateral plus unknown-side members. The vector method is unaffected — it lateral-normalizes at vectorization, so mirror twins are legitimate evidence and both sides are aggregated.

Intra-type reference data

Every search reports the query's intra-type similarity alongside the inter-type rows, so results are always comparable against a same-type baseline:

  • Type queries return the query type itself as the first row (is_intra_type=True). Its similarity is the type's cohesion (mean score of its members against the query vector) and intra_type_similarity is the mean pairwise similarity of the type's members — the intra-type reference every other row is ranked against. n_bodyids gives the member count (NBLAST: ipsilateral plus unknown-side members).
  • bodyId queries tag same-type hits with is_same_type=True and carry the query type's intra_type_similarity on every result row.

In practice (hemibrain v1.2.1, verified 2026-08): aMe12's two members are each other's top hit (0.90 = the intra-type similarity), aMe5 bodyId queries return 10+ same-type members before any inter-type row, and sim(aMe12, aMe10) > sim(aMe12, aMe5) in both directions. Note that single-cell types (e.g. SMP581) can tie or exceed the cohesion of morphologically diffuse types (aMe10, aMe5) — the intra row is a reference, not a guaranteed winner.

3D visualization of the found neurons

Find Similar can render the query and found neurons as interactive 3D skeleton views (same engine as the 3D Skeleton tab and the NeuronBridge FindNeuron visualization).

  • Visualize Top N Types / Neurons (default 10; 0 = disabled): number of top morphology result types/rows to render.
  • Visualize By (default type): type renders one layer per top type, containing all of its member skeletons found in the results (type-level queries resolve members from the vector cache, bounded by BodyIds / Type); bodyId renders one layer per top result neuron.
Analysis-tab visualizations default to Skeleton Mode = line for speed. For high-quality morphology, open Visualization → Skeleton, or change the mode to tube and choose fine with 95% simplification.

When multiple queries are entered, the tab runs them sequentially and saves each query in its own run folder (keep the query to 50 neurons or fewer, and note the search works best on male-cns:v1.0). Morphological output is saved next to its results in {run_folder}/plot-3d_{dataset_folder}/. Each scene starts with a query reference layer, followed by up to the requested top-N result layers. Each layer is colored per type and labeled r{rank}_{type}_x{N} (rank = similarity rank of the type, N = member count). The intra-type reference row is never rendered. The interactive HTML files are listed in the output panel; a visualization failure never discards the search results.

Output

Each run is saved in its own timestamped folder with two always-written result tables:

{output_dir}/similar-morphology_flywire_FAFB_v783_aMe12_20260815_143601/
  results.csv, type_summary.csv, README.txt
  • results.csv always holds bodyId-level similarities (ranked target_bodyId rows), whatever the query kind. A type query includes unique intra-type bodyId pairs for every resolved query member, followed by the top inter-type bodyId rows.
  • type_summary.csv always holds type-level similarities (one row per target type, the query type first as the intra-type reference with is_intra_type=True), whatever the query kind. Type searches rank the top-N types over the whole cached skeleton population (connection candidates + cached skeletons), so the result is not capped at the candidate types.
Exported run guide: every successful run also writes _UserGuide_please_read_me.html into the run folder — a self-contained explanation of every output file, every table column, and any warnings recorded for the run. Format (html / txt / markdown / disabled) is set in Settings → Default Settings → Run Guide Format.
